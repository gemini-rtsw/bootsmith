Using bootsmith

Bootsmith opens a crate's serial console through a WTI terminal server, catches the crate's reboot, stops the auto-boot at the boot prompt, writes the boot parameters from a preset, and boots it.

  1. Connect. Open the system (e.g. GNIRSCC) and press Connect next to the console you want. The dialog names the system, preset and console: check them before you press OK. Connecting does nothing to the crate.
  2. Pick the preset in the session header if the one shown isn't the one you want (e.g. -new-bootserver vs production). Switching keeps the connection.
  3. Reboot the crate with Reboot in the session header. It sends the preset's reboot keys (Ctrl-X on vxWorks unless the preset says otherwise) and asks first, naming the crate. You can also type the reboot in the console. When the boot ROM starts bootsmith sends the abort key, and the state turns AT PROMPT.
  4. Push to board writes every parameter of the preset and reads them back. Any field that didn't read back is listed.
  5. Boot (@ on vxWorks, NBO on PPCBug) starts the IOC with those parameters. The state turns OS running and Push is switched off until the crate is back at its boot prompt, so a second push can't be typed into the IOC shell.
  6. Disconnect when done. The crate keeps running.

Bootsmith asks for confirmation before Connect and before anything that reboots a crate (Boot, Reboot, a typed reboot/reset/exit, Ctrl-X), and before deleting a preset or connection. Pushes and other typing don't ask: once connected you have already confirmed the crate.

Sharing. A console opened in a second tab or by a second person is shared: everyone sees the output and can type. Only one push runs at a time per console. Closing a tab releases its share within about 10 s; an idle tab (no page open) is dropped after 10 minutes. An open tab never times out, and the connection survives a crate reboot.

Freeing a console. The terminal server takes one client per port, so while any bootsmith tab has a console open nothing else (telnet, another tool) can get on. If a tab was left open somewhere, press Disconnect all next to that console in the system list. It drops every tab on it (they are told why) and frees the port; the crate keeps running. It is refused while a push is running.

Hover over buttons, the state pill and boot-parameter names for a short explanation.

Console states

waiting for promptConnected. Waiting for the crate to reboot.
…Reboot seen; sending the abort key to stop the auto-boot.
AT PROMPTAt the boot ROM prompt ([VxWorks Boot]:, PPC1-Bug>). Push and Boot are allowed.
OS runningBooted, or a push found no boot prompt. Press Reboot (or reboot from the console) to push again.
no prompt detectedThe reboot was seen but the prompt never came (12 s). Reboot again, or press Enter in the console and try again.

Before every push and Boot, bootsmith sends one Enter and checks the reply ends in the boot prompt. If it doesn't, nothing else is sent.

Presets and connections

  • A preset is one JSON file: a name, its system, the loader (VxWorks or RTEMS/PPCBug), the consoles it may be used on, and the boot parameters. Example: MKO-PROD-GNIRSCC (production, boots from pisces-control) and MKO-PROD-GNIRSCC-new-bootserver.
  • A connection is a console, a terminal server host:port. Connections belong to one system and are never shared between systems, so a GMOS preset can't be pushed to an MCS crate.
  • The Used on (preset dialog) and Used by (connection dialog) checkboxes are the same thing seen from both sides: which presets list that console.
  • Reboot (preset dialog) is what reboots the crate from its running OS, typed as on the console:
    • ^X is Ctrl-X. Any ^letter is that control key (^C, and ^[ is Esc).
    • Text is sent followed by Enter: exit (RTEMS, EPICS 7), dbpf ag:iocStats:SysReset 1 (3.14 with iocStats; use that IOC's prefix).
    • Blank: Ctrl-X on vxWorks. RTEMS has no default, so the Reboot button stays off until it is set. Leave it blank for crates that only reboot from their bootbar, and say so in the preset name or notes.
    The Reboot button is off at the boot prompt (use Boot there). Before it sends anything, bootsmith presses Enter and refuses if the boot prompt answers, so exit never lands in PPCBug.
  • + New system creates the system with its first console and preset.

Saving in bootsmith writes the files on the server (/var/lib/bootsmith/profiles) immediately. It doesn't touch any crate and doesn't commit to git: do that next.

Saving presets to git

Presets live in github.com/gemini-rtsw/bootsmith-config (public: no passwords in presets). The server directory is a clone of it. Commit what you changed the same day, so the server and git never drift.

Commit changes made in bootsmith

ssh -A mkoswgdkr-lv1.hi.gemini.edu        # -A: your GitHub key does the push
cd /var/lib/bootsmith/profiles
git status                                 # what changed
git diff                                   # check it
git pull --rebase                          # take others' changes first
git add -A
git commit -m "GNIRSCC: point new-bootserver preset at 10.2.2.145 (REL-1234)"
git push

If git push is rejected because main is protected, push a branch and open a pull request instead:

git switch -c REL-1234
git push -u origin REL-1234                # open the PR from the link git prints
# after it is merged:
git switch main && git pull

Changes made on GitHub (a merged PR)

cd /var/lib/bootsmith/profiles && git pull && git log --oneline -1

No restart is needed: bootsmith reads the files on every page load. Delete any copied-in (scp) preset files before git pull or it will refuse to overwrite them.

Testing a preset branch for a TR

git fetch origin REL-1234:REL-1234 && git checkout REL-1234
# ... TR ...
git checkout main

Rolling out a new version of bootsmith

Code is in github.com/gemini-rtsw/bootsmith. Merging a pull request to main makes gemini-rtsw-ci build an RPM and a container image named after the merge commit: bootsmith-0.1.0-3.git<hash>.el9.noarch.rpm and ghcr.io/gemini-rtsw/bootsmith:0.1.0-git<hash>. Wait for the Actions run to finish, then on mkoswgdkr-lv1:

# 1. Refresh the local RPM mirror (port 8081)
docker pull ghcr.io/gemini-rtsw/rpm-repo:latest
docker rm -f rpm-repo
docker run -d --name rpm-repo --restart unless-stopped -p 8081:8080 \
  --log-opt max-size=10m --log-opt max-file=3 ghcr.io/gemini-rtsw/rpm-repo:latest
docker exec rpm-repo sh -c 'ls /usr/share/nginx/html/rpm-repo/ | grep bootsmith'

# 2. Install the RPM
sudo dnf --disablerepo='*' install --nogpgcheck \
  http://localhost:8081/rpm-repo/bootsmith-0.1.0-3.git<hash>.el9.noarch.rpm
rpm -q bootsmith

# 3. Pull the image and restart (the RPM does neither)
docker pull ghcr.io/gemini-rtsw/bootsmith:0.1.0-git<hash>
sudo systemctl daemon-reload && sudo systemctl restart bootsmith
docker ps --format '{{ '{{' }}.Image{{ '}}' }}' --filter name=bootsmith
sudo journalctl -u bootsmith -n 20 --no-pager

It worked when rpm -q and docker ps both end in git<hash> and the journal ends with Listening at: http://0.0.0.0:8080. The footer of this page shows the running image. Then hard-refresh the browser (Ctrl-Shift-R).

  • Check nobody is mid-boot first: the restart drops every open console.
  • dnf refuses with "a higher version is already installed"? rpm sorts the hash as text, so a newer build can look older. Use sudo dnf --disablerepo='*' downgrade --nogpgcheck <same url>. Run install first; only use downgrade when dnf says so.
  • Image pull times out (dial tcp ...:443: i/o timeout): run it again; GHCR has several addresses and one is sometimes unreachable.
  • Rollback: install the previous RPM the same way, pull its image, restart.

Troubleshooting

“… is not at its boot prompt … nothing was sent”
The crate is running its OS. Reboot it from the console and wait for AT PROMPT.
Connect takes long or fails
About 11 s when the port refuses, up to 40 s when it times out. Someone else (or a stuck telnet) may hold the WTI port, or IT hasn't opened the port to mkoswgdkr-lv1. Press Cancel to stop.
Telnet to the WTI port is refused
Bootsmith probably has it open in a tab somewhere (the system list shows “open in N tabs”). Press Disconnect all there.
“unit_number” didn't read back on an mv167
The vxWorks 5.2 ROM has no unit-number field. Harmless.
A few blank prompts appear on the crate's console log
That is bootsmith connecting (it sends Enter to find the prompt). It doesn't reboot anything.
Who pushed what, and when
sudo journalctl -u bootsmith --since "YYYY-MM-DD HH:MM" --until "..." --no-pager on mkoswgdkr-lv1. The crate side is in TED: Press any key to stop auto-boot, then c and p.
